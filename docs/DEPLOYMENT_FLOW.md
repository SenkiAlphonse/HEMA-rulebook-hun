# Deployment Flow

## Overview

The HEMA Rulebook application uses a **build-then-deploy** workflow to ensure rule changes are processed and indexed before the application starts.

## Build Artifacts

Two critical artifacts are generated during the build process:

1. **`data/search/rules_index.json`** - Searchable rule index with metadata
2. **`dist/rulebook.html`** - Pre-rendered rulebook HTML

After the repo re-org, the index artifact lives at **`data/search/rules_index.json`**.

These artifacts are generated by running:
```bash
python build.py
```

## Deployment Platforms

### Render.com (`render.yaml`)

**Build Command** (runs during deployment):
```bash
pip install -r requirements.txt && pytest tests/ -v && mkdir -p dist && python build.py && ls -la dist/rulebook.html
```

**Start Command** (runs to start the service):
```bash
gunicorn --bind 0.0.0.0:${PORT:-10000} --workers ${WEB_CONCURRENCY:-1} wsgi:app
```

**Key Points:**
- Build artifacts are generated fresh on every deployment
- Tests must pass before build artifacts are created
- The build command runs in Render's build environment (cached dependencies)
- The start command runs in the production environment (with pre-built artifacts)

### Heroku/Generic (`Procfile`)

**Release Phase** (runs after build, before web dynos start):
```bash
release: python build.py
```

**Web Process**:
```bash
web: gunicorn --bind 0.0.0.0:${PORT:-10000} --workers ${WEB_CONCURRENCY:-1} wsgi:app
```

## GitHub Actions (`.github/workflows/test.yml`)

The CI/CD pipeline runs on push to `main` and `ai-agent` branches:

1. **Test Job** - Runs all tests to verify code quality
2. **Build Job** - Generates build artifacts and verifies they exist
3. **Commit Artifacts** (main branch only) - Auto-commits updated artifacts with `[skip ci]`

**Why Auto-Commit?**
- Keeps the repository in sync with the latest processed rules
- Allows quick rollback to any version with matching artifacts
- Enables deployment platforms to use pre-built artifacts (faster deploys)

## Local Development

### Running the Build Manually

```bash
# Rebuild search index and pre-rendered rulebook
python build.py

# Run the app with fresh artifacts
python wsgi.py
```

### Testing Before Commit

```bash
# Run tests
pytest tests/ -v

# Build artifacts
python build.py

# Verify artifacts exist
ls data/search/rules_index.json
ls dist/rulebook.html
```

## When Rules Are Processed

Rules are **re-processed** in the following scenarios:

1. ✅ **On every Render deployment** (via `buildCommand`)
2. ✅ **On every Heroku release** (via `release` phase in Procfile)
3. ✅ **On every CI build** (via GitHub Actions)
4. ✅ **When you run `python build.py` locally**

Rules are **NOT** re-processed when:
- ❌ The Flask app restarts (uses cached artifacts)
- ❌ You edit a markdown file without rebuilding

## Troubleshooting

### Build artifacts not updating on deployment

**Symptoms:** Rule changes don't appear after deploying

**Causes:**
1. Build command not running (check Render/Heroku logs)
2. Build script failing silently (check exit code)
3. Old artifacts deployed (not rebuilt during deploy)

**Solutions:**
1. Check deployment logs for `python build.py` output
2. Verify `buildCommand` in `render.yaml` or `release` in `Procfile`
3. Manually run `python build.py` and commit artifacts

### GitHub Actions not committing artifacts

**Symptoms:** Auto-commit step fails or skips

**Causes:**
1. Missing `permissions: contents: write` in workflow
2. Build artifacts unchanged (no diff to commit)
3. Branch protection rules preventing push

**Solutions:**
1. Add `permissions: contents: write` to workflow
2. Check if artifacts actually changed (this is normal)
3. Configure branch protection to allow github-actions[bot]

## Best Practices

1. **Always run `python build.py` after editing rules locally**
2. **Commit build artifacts along with rule changes** (auto-committed on main)
3. **Verify build logs on deployment** to ensure processing succeeded
4. **Test locally before pushing** to catch issues early
